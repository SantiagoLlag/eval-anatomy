# Architecture

eval-anatomy is a web app plus a catalog. It does three things with any eval:

1. **Anatomy** — shows the theoretical parts every eval has (16 parts in 5 groups), with definitions, best practices and sources.
2. **Your eval** — takes a concrete eval (from the catalog, an uploaded file in a known format, or pasted free text), maps it onto those 16 parts, shows what is present, partial or missing, and reviews it against research-backed rules.
3. **Flow** — draws how that eval actually runs, from cases to decision.

The catalog is a folder of evals (`catalog/<id>/eval.md`) that anyone can contribute by pull request.

## Sources of truth

| What | Where | Who edits it |
|---|---|---|
| Anatomy, taxonomy, rules, tool field maps, sources | `content/*.json` | **Generated.** Never hand-edit. Regenerated by the owner from a private research vault with `scripts/generate_content.py`, which enforces traceability (every rule and part cites verified sources). If something is wrong, open an issue. |
| Eval card format | `schema/eval.schema.json` | Changes need an issue first; bump `schema` version on breaking changes. |
| Catalog evals | `catalog/<id>/` | Contributors, via PR. CI validates every card. |
| Native-format examples | `research/fixtures/` | Generated copy of research fixtures; the same "support assistant must not invent policies" eval written in 10 tools' native formats. Use them as importer test fixtures. |
| Prior art | `docs/reference/agents-visualizer/` | Read-only reference code from a sibling project that solved the same problems for agent architectures. Not built, not imported. Copy patterns, not files. |

## Stack

- Next.js (App Router, latest major) + TypeScript (strict) + Tailwind CSS v4 + shadcn/ui.
- zod v4 for runtime schemas. `yaml` + `gray-matter` for parsing.
- `@xyflow/react` + `@dagrejs/dagre` for diagrams.
- AI SDK (`ai` + `@ai-sdk/anthropic`) for the two LLM features. Default model `claude-sonnet-5-5` (override with `EVAL_ANATOMY_MODEL`).
- vitest for tests. GitHub Actions for CI. Deploy on Vercel.
- Read `node_modules/next/dist/docs/` before writing Next.js code: the installed major may differ from your training data.

## Content model (`content/*.json`)

All user-facing research text is bilingual: `{ "es": "...", "en": "..." }`.

- `anatomy.json`: `groups[]` (5), `parts[]` (16: `id, group, level, levelNote?, condition?, name, oneLine, explanation, whyItMatters, bestPractices, commonMistakes, example, synonyms, sources[]`), `relations[]` (`from, to, kind: flow|control|defines, label`), `decision` (terminal node), `runningExample`.
- `taxonomy.json`: `axes[]` (`id, filter, multiple, name, note?, values[{id, label, definition?, note?}], sources[]`) and `constraints[]` (combinations the sources fix; the linter may use them).
- `best-practices.json`: `rules[]` (`id, part, severity: error|warn|info, detection: deterministic|llm-judge|human|requires-run, check, appliesIf, statement, rationale, sources[]`). `check` is the human-readable spec of the deterministic check against the eval card.
- `tools.json`: per tool `id, name, format: declarative|code, detection{strong[], weak[]}, fields{partId: native field name | null}, fixture, notes, deprecatedOn?`, plus `openaiNote` (OpenAI Evals platform shuts down 2026-11-30).
- `sources.json`: `sources{id: {title, authors[], url, type, evidence, status, lens, verified}}`. Every `sources[]` id anywhere resolves here. Show them as citations with links.

Part ids: `purpose, cases, reference, system, environment, output, criteria, grader, verdict, trials, aggregation, threshold, baseline, validation, metadata, documentation`.

## Core in-memory model

```ts
type PartStatus = "present" | "partial" | "missing" | "not-applicable" | "inferred";

interface DecomposedEval {
  card: Partial<EvalCard>;          // zod-parsed canonical frontmatter (src/lib/schema/eval.ts mirrors schema/eval.schema.json)
  body?: string;                    // markdown body, if any
  sourceFormat: ImporterId;         // canonical | vault-evals | promptfoo | openai-evals-registry | openai-evals-api | lm-eval | elevenlabs | inspect | deepeval | braintrust | freeform
  coverage: Record<PartId, { status: PartStatus; from?: string; note?: string }>; // `from` = where in the source it came from (field path / line)
  warnings: string[];
}
```

`computeCoverage(card, anatomy, taxonomy)` is pure and shared by all views:

| Part | present when | partial when | not-applicable when |
|---|---|---|---|
| purpose | `question` and `construct` | only one of them, or only `summary` | — |
| cases | `count>0` or `examples` or `file` | present but no `source` | `taxonomy.moment = online` and `sampling` set |
| reference | `kind` ≠ none | kind set, no `produced_by` | no criterion/grader compares against a reference and `judgment ≠ pointwise-reference` |
| system | `prompt` or `model` | only `description` | — |
| environment | `description` and `reset_per_trial` | only one | `structure` not agent-* |
| output | always `inferred` unless the source format records outputs/transcripts | — | — |
| criteria | ≥1 criterion with `question` | criteria without examples | — |
| grader | ≥1 grader and every criterion links to one | some criteria unlinked | — |
| verdict | `scale` (+ anchors if ordinal) | ordinal without anchors | — |
| trials | `k` and `metric` | only `k` | output is deterministic (no agent, temperature 0) |
| aggregation | `method` and `uncertainty` | `method` only | — |
| threshold | `per_case` or `overall` or `gates` | — | `taxonomy.purpose = capability` |
| baseline | `kind` ≠ none | — | — |
| validation | `judge_vs_human` or `planted_failures` or `reference_solution` | — | no llm-judge/human grader and origin ≠ public-benchmark |
| metadata | `version` and `history` | one of them | — |
| documentation | `license`, `authors`, `contact`, `limitations` | some | — |

Keep this table in code as data, with a unit test per row.

## Importers (`src/lib/importers/`)

- `detectFormat(file: {name, text})` scores each tool's `detection.strong/weak` from `tools.json` plus the canonical signature (`schema: eval-anatomy/v1`) and the vault signature (frontmatter with `id`, `dimension`, `aplica_a` and the 8 numbered `## ` sections). Return ranked candidates; the UI lets the user override.
- One parser per format returns `DecomposedEval`. Declarative formats (canonical, vault-evals, promptfoo, OpenAI registry/API, lm-eval, ElevenLabs) are parsed directly. Code formats (Inspect, DeepEval, Braintrust) get a best-effort static parse (regex/AST-lite over `Task(...)`, `Eval(...)`, `GEval(...)`, `LLMTestCase(...)`) and mark everything else `missing`; the UI offers the LLM path to fill gaps.
- `freeform`: `POST /api/decompose` with the text; the server calls the model with `generateObject` and a zod schema equal to `EvalCard` plus per-part `{status, from}`. The prompt must forbid inventing: absent parts stay absent.
- Field names per tool come from `tools.json.fields`; parsers must not invent fields. Known traps are in `tools.json.notes` (promptfoo accepts unknown keys; lm-eval `!function` tags; Ragas `rubrics` plural; `task` means different things per tool).
- Tests: every fixture in `research/fixtures/` must import and produce the expected coverage snapshot.

## LLM features and keys

Two server routes: `/api/decompose` (free text → card) and `/api/lint/llm` (runs `llm-judge` rules over a card). Key resolution order: `ANTHROPIC_API_KEY` env → `AI_GATEWAY_API_KEY` env / Vercel deployment → a key the visitor pastes in the UI, sent per request in the `x-anthropic-key` header, kept only in memory (never localStorage, never logged, never echoed). If no key is available, hide LLM buttons and say why. Everything else works without any key.

## Linter (`src/lib/lint/`)

Same pattern as `docs/reference/agents-visualizer/src/lib/lint/`: rules come from `content/best-practices.json`; deterministic rules are functions keyed by rule id in `deterministicRules.ts` (one unit test each, pass and fail); `appliesIf` is evaluated against `card.taxonomy` and present parts (`parts`), and `catalog: true` rules apply only to catalog entries. `human` rules render as a checklist for the reader. Findings carry `ruleId, part, severity, message (bilingual from rule.statement), sources`.

## Diagrams

- **Anatomy view**: fixed, stable layout (not auto-layout): five bands left→right by group (`intent → inputs → judgment → conclusion → governance`), parts as nodes coloured by group, `relations` as edges (flow = solid, control = dashed, defines = dotted), plus the `decision` terminal node. Clicking a node opens a side panel (definition, why it matters, best practices, common mistakes, example, synonyms, sources). Used twice: empty (theory) and overlaid with a `DecomposedEval` (each node shows its status badge and the eval's actual content).
- **Flow view**: `buildFlowGraph(card)` derives a run graph and lays it out with dagre LR: cases(n, tags) → [environment] → system(model/prompt) → output → one node per grader (coloured by kind: code, similarity, llm-judge, human, user-signal) fed by its criteria; reference edge dashed and only into graders that use it; validation as a dashed edge from outside the run into judge nodes with a badge (e.g. "TPR 0.90 · TNR 0.95 · n=100"); verdict → trials(k, metric) → aggregation(method ± uncertainty) → threshold/gates → decision. Missing parts appear as ghost nodes with a dashed border and a "missing" label, never silently dropped.

## Routes

`/[locale]` with `locale ∈ {es, en}` (default `es`, detect from `Accept-Language`, switcher in the header).

| Route | What |
|---|---|
| `/` | What an eval is in one screen; entry points to Anatomy, Catalog, Inspect |
| `/anatomy` | Theoretical anatomy view |
| `/catalog` | Catalog list with filters = taxonomy axes where `filter: true` |
| `/catalog/[id]` | Eval detail: tabs Anatomy (your eval) · Flow · Review (linter) · Card (rendered body) · Source (raw) · Export |
| `/inspect` | Upload or paste any eval → same tabs as detail, client-side; "Save as eval.md" |
| `/sources` | All research sources with evidence level and links |

Catalog pages are statically generated at build time from `catalog/`.

## Conventions

- UI text: `messages/es.json` and `messages/en.json`; no hard-coded strings. Research text always comes from `content/*.json`. An eval's own text is shown in its own `language`.
- Spanish UI copy follows plain-language rules: short sentences (≤ 20 words average), define technical terms on first use, no vague praise words.
- Accessibility: keyboard-navigable diagrams (each node focusable, panel opens with Enter), colour never the only signal (status also as text/icon), WCAG AA contrast, works at 375 px width.
- No secrets in the repo. No analytics without consent.
